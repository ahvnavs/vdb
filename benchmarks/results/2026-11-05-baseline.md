# VDB performance baseline — 2026-11-05

This is an engineering baseline, not a release performance claim. The checkout
had uncommitted work from the current development series. Commit at measurement
time: `96238dc`.

## Environment

- Host: WSL2 Linux 6.18.33.2, x86_64, ext4 on `/dev/sdd`
- CPU: 13th Gen Intel Core i5-1335U; 4 logical CPUs exposed, 2 cores, 2 threads
  per core; 12 MiB L3
- Memory: 5.8 GiB RAM and 2.0 GiB swap; approximately 1.7 GiB swap was in use
- Rust: rustc 1.99.0 (b940084d7, LLVM 23.1.1); cargo 1.99.0
- Criterion: 20 samples, 1 s warm-up, 2 s target measurement
- Plot backend: plotters (`gnuplot` unavailable)
- Low-level profilers: `perf`, Valgrind, and heaptrack unavailable

The machine was not isolated, CPU frequency was not pinned, and the OS page
cache was not cleared. Confidence intervals capture sampling uncertainty but
not all system noise.

## Process resource profile

Each process inserted 10,000 documents of 1,024 bytes, 100 documents per
transaction. Amplification is total database-directory bytes divided by
10,240,000 logical payload bytes. Milliseconds include population and, for VDB,
client-side envelope construction; they are diagnostic rather than a fair
throughput comparison.

| Engine | Elapsed | Peak RSS | File bytes | Amplification |
| --- | ---: | ---: | ---: | ---: |
| VDB | 393 ms | 41,744 KiB | 67,375,104 | 6.5796x |
| SQLite WAL/FULL | 38 ms | 7,020 KiB | 13,963,264 | 1.3636x |
| direct redb | 40 ms | 18,540 KiB | 16,846,848 | 1.6452x |

VDB file and memory amplification are the clearest measured follow-up areas.
They include encrypted-envelope expansion and durable metadata/history/index
structures absent from the baseline schemas. This run did not establish which
internal allocation dominates, so no speculative storage-format change was
made.

## Baseline defects and optimization decision

The first mixed-workload run reused IDs between Criterion phases and correctly
hit VDB's version-conflict check. The harness now allocates monotonically unique
round IDs; the corrected workload completed. This was a benchmark defect, not a
database defect.

No database hot path was modified. The available profile demonstrates costs but
does not isolate a correctness-preserving implementation bottleneck below the
required cryptographic and durability work. The next performance task is to run
a sampling/allocation profiler on batch commit and file growth, then optimize
only a measured internal hot path and retain this baseline for comparison.
